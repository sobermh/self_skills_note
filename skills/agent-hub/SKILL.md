# 精简多 Agent 协作

采用一个主控、按模块负责的 Agent，不额外引入角色体系或治理流程。

## 开工

1. 有 `agent-hub/` 时读 README.md、owners.md 和自己的进行中单子，需要共享事实再读 knowledge.md。默认不读归档。
2. 没有时，在用户要求建立此协作方式的范围内创建精简的四类内容：README.md（规则）、owners.md（主控与路径归属）、knowledge.md（当前共享事实）、tickets/（一件事一张单）。不生成空目录或额外台账。
3. 主控名称和负责人使用用户指定的名字；未指定时采用项目前缀。名称只是协作身份，不表示已经创建了用户侧会话。

## 分工与派单

- 主控负责接口、拆单、跨模块协调、联调与复核。负责人只改约定路径及自己的单子；需要改别人路径时先向主控提出。
- 主控先检查脏工作区，明确现有改动和禁止触碰内容。避免两个 Agent 同时写同一文件；测试、文档也要明确归属。
- 单子保持短小：状态、负责人、目标、负责范围、验收标准、不要碰、回执。证据不足就写未确认，不把猜测写成事实。
- 使用当前环境的子 Agent 工具实际派发，并记录返回的 Agent 标识；写单子不等于已派发。只有用户明确要求新建独立聊天时才创建用户侧聊天。
- 派发消息包含项目绝对路径、单号、允许修改的范围、验证要求和禁止操作。不继承超出当前任务的历史授权。

## 回执与验收

状态：待处理 → 进行中 → 待验收 → 已完成；无效需求标记作废。

- 负责人接单、实施、自测，回执写明改动文件、验证结果、未解决事项及共享事实提议；不能自行宣称用户验收通过。
- 主控检查接口兼容、测试证据和实际差异，必要时退回修正。用户确认或明确委托验收后才结单；结单后有需要再归档。
- 提交、推送、部署、正式数据写入、生产操作仍按用户授权，不由派单或 skill 自动获得。
- 汇报区分已派发、开发中、已验证、已部署；不把计划说成结果。

## 保持简单

- 信息只放一处：范围在 owners，任务在单子，共享事实在 knowledge，使用说明在服务文档。
- knowledge 只保留跨模块当前事实，写来源或复核时机；负责人提议，主控核实维护。不得保存密钥。
- 用户当前指示优先；需求变化改写当前单子，不堆历史日志。不要把其他项目特有规则、路径或角色照搬进来。
