# 两层 Bug 台账规则

Bug 台账记录已经发现、能够描述证据和影响的产品或工程缺陷。它不是普通开发 Todo 的替代品：Todo 管“要做什么”，Bug 台账管“什么行为不符合预期、为何发生、如何修复并验证”。

## 登记边界

满足任一条件就登记 Bug：

- 用户可见行为错误、核心流程中断或已有能力回归。
- QA/Beta 验收失败，或任务验收标准因实现缺陷未满足。
- 安全、权限、数据一致性、并发、恢复、资源边界或可观测性缺陷。
- 会影响发布判断、需要跨会话追踪，或修复后必须保留回归证据的问题。
- 同一确定性问题重复出现，不能再只留在聊天、日志或开发者记忆中。

尚无证据的猜测先记在任务卡风险中；在提交或交接前即时发现并修正、从未形成可运行错误行为的拼写或编译错误，不必单独建 Bug。拿不准时优先登记，避免问题随上下文消失。

## 默认文件布局

新项目默认使用：

```text
develop/bug/
├── README.md
├── todo-bug.md
└── todo-bug-M<N>.md
```

- `README.md`：薄的项目入口，只记录本项目路径、验证命令和例外；通用规则引用本文件，不复制全文。
- `todo-bug.md`：全局索引和状态投影，只保存 ID、标题、严重级别、状态和明细链接，以及里程碑计数。
- `todo-bug-M<N>.md`：里程碑完整 Bug 记录的唯一正文来源；首次登记该里程碑 Bug 时创建。

已有项目采用其它成熟路径时，upgrade 保留路径并写入项目 delta，不为统一目录搬家。无论路径如何，必须保持“短索引 + 按里程碑完整明细”两层职责。

## ID、严重级别和状态

默认 ID：`BUG-M<里程碑>-<三位序号>`，例如 `BUG-M6-007`。

- 序号属于该里程碑编号空间，从 `001` 开始，取历史最大号加一。
- ID 是永久身份，不随排序、状态或文件移动变化；空号不回填，已关闭、作废或接受风险的 ID 不复用。
- 跨里程碑处理时保留原 ID，在记录的“里程碑”字段补充实际修复归属。
- 新引用必须使用完整 ID，不能只写“第 7 个 Bug”或标题。
- 序号和索引计数只表示已登记记录，不代表项目只有这些 Bug，也不预测尚未发现的问题数量。

严重级别：

| 级别 | 默认含义 |
|---|---|
| P0 | 阻断发布，或造成安全、数据、不可恢复事故、系统整体不可用 |
| P1 | 核心路径不可用、广泛回归或高风险失败，没有合理绕行 |
| P2 | 明显功能/可靠性缺陷，但存在有限绕行或影响范围受限 |
| P3 | 低影响体验、文案、维护性或边缘行为问题 |

状态机：

```text
open -> fixed -> verified
  |        |
  +------> accepted
```

- `open`：已确认并待修，或 QA 回归失败后重新打开。
- `fixed`：Developer 已完成修复和开发侧验证，等待独立 QA/真实环境回归。
- `verified`：QA 已按回归门验证通过。
- `accepted`：明确接受风险、不修或延期；必须记录 Architect 或用户的决定、理由和重新触发条件。

不得从 `open` 直接写成 `verified`。修复实现者的自测不能替代 QA；QA 回归失败时改回 `open`，保留历次修复和失败证据。

## 角色所有权

- 任何角色在允许项目文档写入的会话中发现达到登记边界的问题，都要在本次交接前创建或更新 `open` 记录，不能只写在最终报告里。Audit 或用户明确要求只读时只报告建议记录和证据，不写文件。
- 发现者先按严重级别表填写暂定级别，不因等待裁决而延迟登记；Architect 负责处理级别争议，并裁决范围、目标里程碑、跨任务依赖和 `accepted` 建议，涉及产品取舍时由用户拍板。
- Developer 负责根因、实际修复记录、聚焦测试和 `open -> fixed`；不得自行写 `verified` 或静默接受风险。
- QA 负责复现证据、独立回归、`fixed -> verified`，失败则 `fixed -> open` 并追加结果。
- Beta 发现发布级问题时登记 Bug，并据其级别和状态给出 `GO / CONDITIONAL GO / NO-GO`；不得只留在发布报告。

## 写入顺序和单一事实源

1. 在对应里程碑明细中创建完整记录，初始状态通常为 `open`。
2. 同步全局索引行和里程碑状态计数。
3. 发现者在现有 Todo 卡的 `关联 BUG` 和失败/风险证据中追加 ID，并在 Bug 的“里程碑”字段反向引用 step_id；这不授权其修改任务目标、范围、设计决策或验收标准。设计、测试计划和发布清单只引用 BUG ID 与一句结论，不复制现象、根因和修复正文。
4. Developer 修复后，在同一记录追加根因、修复内容和开发侧测试，状态同步为 `fixed`。
5. QA 在同一记录追加独立回归证据；通过改为 `verified`，失败改回 `open`。

索引是投影，不是第二份事实源。标题、严重级别或状态变化时，明细标题、明细字段、索引行和计数必须同次更新。

## 索引模板

```md
# <PROJECT> Bug Ledger

> 全局索引/状态投影；完整记录见对应里程碑文件。

## 里程碑计数

| 里程碑 | open | fixed | verified | accepted | 合计 | 明细 |
|---|---:|---:|---:|---:|---:|---|
| M0 | 0 | 0 | 0 | 0 | 0 | [M0](todo-bug-M0.md) |

## 缺陷索引

| ID | 标题 | 级别 | 状态 | 明细 |
|---|---|---|---|---|
| BUG-M0-001 | <一句话标题> | P2 | open | [M0](todo-bug-M0.md) |
```

没有 Bug 的里程碑不必提前创建明细文件或计数行。

## 明细模板

```md
# <PROJECT> <MILESTONE> Bug Ledger

### [open] BUG-M0-001 <一句话标题>

- 里程碑：<step_id / 验收活动 / 修复归属>
- 严重级别：P0 / P1 / P2 / P3（简述判断依据）
- 状态：open / fixed / verified / accepted
- Owner：<修复责任方>
- 发现方式：<日期、角色、运行环境、测试用例或用户报告>
- 复现/证据：<最小复现步骤、输入条件和观察证据>
- 现象：<实际行为与预期行为的差异>
- 影响：<业务、安全、数据、可靠性或发布影响>
- 根因：<定位到模块/契约；未定位时写“待定位”>
- 修复记录（<日期>，Developer）：<实际文件、行为和边界>
- 回归测试（<日期>，QA）：<命令/环境、结果和失败路径>
- QA 门：<从 fixed 到 verified 必须满足的可执行条件>
```

创建 `open` 记录时允许“根因、修复记录、回归测试”写为待补；复现/证据、现象和影响不能省略。记录中不得放真实密钥、客户隐私、内部凭据或可直接滥用的攻击载荷。

## Todo、测试与发布联动

- 缺陷直接导致当前卡验收失败、且修复仍在原范围内时，Architect 重开原卡；缺陷跨卡、超出原范围、需要独立设计/发布节奏或原卡已归档时，Architect 创建独立修复卡。两者都在 `关联 BUG` 字段引用 ID。
- Bug 记录的“里程碑”反向引用 step_id 或验收活动，形成双向导航。
- QA 因该缺陷判定任务不通过时，Todo 卡保持或改为 `qa-fail`，直到修复重新交验；登记 Bug 本身不能把失败任务标记完成。
- 测试计划记录用例和 PASS/FAIL；失败事实、根因、修复历史仍只在 Bug 明细展开。
- 未解决 P0 默认阻断发布；未解决 P1 默认 `NO-GO`，除非用户明确接受风险；P2/P3 按项目 Release Gate 裁决。
- 关闭任务卡不自动关闭 Bug；只有上述状态所有者可以推进 Bug 状态。

## 上下文装载

处理缺陷时默认只读取：

1. 项目规则和 workflow delta。
2. Bug 总索引。
3. 当前或明确指定里程碑的 Bug 明细。
4. 当前 BUG 记录明确引用的 Todo、设计、测试和代码。

不得默认加载全部历史 `todo-bug-M*.md`。查询单个状态时先在索引定位，再读取该记录附近的最小范围。

## Bootstrap、Upgrade 与守门

- Bootstrap 创建 `develop/bug/README.md` 和空的 `todo-bug.md`；里程碑明细在首次登记时创建。
- Upgrade 识别现有缺陷文档，保留已有 ID、路径、状态和历史；只收敛职责和未来写入规则，不为统一格式批量重写历史。
- 多 Agent、高频维护或已发生台账漂移的项目，应提供结构守门测试。最低检查：ID 全局唯一、ID 与里程碑文件匹配、索引/明细标题级别状态一致、计数准确、必填字段存在。
- 守门还应检查新加入的 `BUG-M<N>-<NNN>` 文档引用能够解析到索引记录。旧项目存在历史悬空引用时，可使用有说明的临时 legacy allowlist，但不得允许新增悬空引用。
- 台账变更后运行项目 delta 中声明的聚焦守门命令；没有自动化守门时，按同一检查项人工审计。
