# 私有 npm 发布要求

## 身份与授权

本生态默认发布到 https://npm.tokensapi.ai/，除非用户明确指定其他目标。不要退回 npmjs.org 发布。
公共 npm 可用于安装公共构建依赖，但不等于发布目标。
从 package.json 读取包身份，从 Git origin 确认获准发布的仓库，将预期身份固定在发布校验中。
拒绝非预期包名、所有者、仓库或 Registry。解析仓库 URL，不用子串包含判断代替身份校验。

CI 发布只使用当前仓库 Secret `VERDACCIO_PUBLISH_TOKEN`。缺少时明确报错，`npm whoami` 必须返回 `tokenscowork`。
凭据只暴露给发布步骤，不暴露给构建或测试步骤。不要输出凭据文件或含 token 的环境变量。
setup-node 的 registry-url 用于生成 npm 认证配置，仅设置 NODE_AUTH_TOKEN 不够。

## 工作流结构

默认将检查与发布分成两个工作流文件，文件名应说明用途；用户已明确指定合并触发或手动重试时，保留其要求并实施同等发布门禁。

- `.github/workflows/checks.yml`：`push` 到 `branches: ['**']` 加 `pull_request`，只跑检查，永不发布。
- `.github/workflows/publish-npm.yml`：默认只吃 `tags: ['v*']`，失败时在 Actions 页面 re-run。用户明确要求手动重试时，`workflow_dispatch` 默认只检查，发布须显式选择已有稳定标签；解析标签到提交 SHA，检查和发布都使用该 SHA。手动与自动发布同一标签必须共用并发键及准确版本不可覆盖保护。

默认结构的分支与标签触发互斥；用户指定其他结构时检查实际触发关系，不以减少检查次数为由移除发布门禁。

检查矩阵使用插件的同一标准功能回归入口（`test/run-test-cases.mjs`，通过实际 `test:cases` 或等价标准命令调用），验证实际发布的提交；失败或用例未完成时不得进入发布步骤。

**`publish-npm.yml` 必须自带一份与 `checks.yml` 相同的检查矩阵。这不是冗余，不要删，也不要改成调用可复用工作流来"消除重复"**：`needs:` 跨不了工作流文件，发布只能 gate 在同一次运行里跑出来的检查上。把这个原因写进文件头注释和发布文档，否则下一个整理 YAML 的人会把它删掉。

矩阵覆盖 package.json `engines` 的最低版本及当前支持的主要版本线，并说明覆盖范围；开放的版本范围不代表未来所有版本已验证。发布步骤本身用其中一个版本即可。

CI 的系统和 shell 必须能实际执行用例。Windows/macOS 安装包用例在 Linux 上跳过时，不得把跳过视为通过；选择支持的 Runner，或在夹具中显式模拟平台。Windows 下 Bash 与 PowerShell 的变量和通配符语义不同，应明确 shell 并验证打包命令。读取 tarball 优先用项目已有的跨平台库；GNU tar 可能将 `C:\\...` 解析为远程主机，不能仅凭本机系统 tar 成功就认定 CI 兼容。

并发键按工作流与 ref 取，发布不允许中途取消：

下面例子适用于默认标签触发；支持手动标签重试时，键中的 ref 改为同一格式的目标标签，避免手动运行的 main ref 与标签推送使用不同锁。

```yaml
concurrency:
  group: ${{ github.workflow }}-${{ github.ref }}
  cancel-in-progress: false   # 仅发布工作流；检查工作流用 true
```

使用 contents: read 和 checkout 的 persist-credentials: false。
只允许确认过的目标仓库发布；目标仓库本身可能是 fork，不要仅因 GitHub 返回 fork: true 就禁止发布。
发布任务保留对稳定标签来源的条件检查，即使触发器已经保证了；用户指定手动发布时，将已验证的已有标签纳入条件，不能仅以手动运行或分支检查成功允许发布。

依赖安装用冻结锁文件，具体命令按目标仓库实际使用的包管理器写，不要照抄其他插件：

- pnpm：先用 `pnpm/action-setup` 装 pnpm（**必须在 setup-node 之前**，否则 `cache: pnpm` 找不到它），再 `pnpm install --frozen-lockfile --ignore-scripts`。
- npm：`cache: npm`，`npm ci --ignore-scripts`。

本生态两种都在用（渐进式工具是 pnpm，插件体检是 npm），先读锁文件确认是哪种。

按需保留兼容性矩阵检查，不要仅为减少 YAML 文件而删掉兼容性覆盖。

## 打包与发布

构建（若该插件有构建步骤）和测试都通过之后再打包，验证实际 tarball、入口和资源。手写并入库的运行时代码没有构建产物，不要为它硬造构建步骤。

**打包命令的每个选项都要在目标仓库的包管理器和版本上实测过再写进 workflow**，同名选项在 pnpm 和 npm 下并不都存在：

- `pnpm pack`（11.x）**没有 `--ignore-scripts`**，传了会以未知选项报错退出；要跳过 `prepack` 必须走 `--config.ignore-scripts=true`（环境变量 `npm_config_ignore_scripts` 对 pack 无效）。
- `npm pack` **支持 `--ignore-scripts`**，直接传即可。

两条都是实测结论，不是文档推断。若 `prepack` 就是全套检查、而检查任务已经跑过，打包时跳过它并在注释里写明原因。给这类容易回归的参数加断言，让它在改错时立刻失败而不是等到发布。

发布已验证的同一份 tarball，关闭发布生命周期脚本，显式指定私有 Registry。默认不上传为公开构建产物。

拒绝覆盖已发布的准确版本。Registry 查询的鉴权、网络或服务端错误不代表版本不存在，应停止发布。
只有确认版本不存在才允许尝试新版本发布，保留 Registry 不可变版本保护和逐标签并发控制。
不要为了让重试成功而撤销发布、覆盖版本或擅自升版本。

发布后查询准确版本和预期 dist-tag，对比 Registry tarball 的完整性与元数据。
202 Accepted 表示正在处理，不代表已可用。有界等待后仍未完成就报告待处理，不重复发布。

存在并发修改或用户要求发布核验时，重新下载准确版本的 Registry 包，核对 SHA-512、入口及实际运行时文件与标签提交的构建输出。处理认证后确认查询成功，再比较元数据；鉴权失败响应缺少 dist 字段不等于包完整性被破坏。核对远程分支、标签解析提交、发布运行及获授权的外层引用；仅有版本号一致不能证明来自同一份代码。

## 版本与变更记录

发布前核对三者完全一致：package.json 的 `version`、标签名去掉 `v` 前缀、变更记录里新增小节的标题版本号。

**小节标题写错版本号是真实发生过的事故**：说明被写在上一个版本的标题下，而同一提交里版本号已经往前走了，那次发布因此在变更记录里没有任何痕迹，事后只能靠拉下已发布的 tarball、比对文件清单来还原它对应哪个提交。

每个发布过的版本都要有自己的小节和对应的链接引用。补写历史版本时依据当时提交的实际 diff，不要从提交信息润色出没发生过的改动；已经写好的邻近小节不要顺手改动。

## 启用与验收

fork 仓库需检查真实 Actions 页面是否有工作流启用确认，不能只看 API 的 active/enabled。
未获授权不要点击启用；无法访问界面时标记未验证。授权推送后检查真实 push 触发的运行。

测试校验器拒绝标签不一致、预发布版本、错误身份和错误 Registry。
**这类测试里的版本号一律从 package.json 派生（`v${manifest.version}`），不要硬编码当前版本**：硬编码的用例在写下时是过的，第一次 bump 版本才会假失败，而那正好是你在发布路上最不想被拦的时刻——实际发生过一次。
不执行真实发布也应测试已存在版本拒绝与查询错误处理。
解析工作流 YAML 或使用可用校验器，仅匹配源码字符串不能证明工作流正确。

报告区分本地检查、远程分支检查、发布工作流里的检查和实际 Registry 发布。
未经发布授权，不要为了测试 CI 创建发布标签。仅修改工作流时保持现有包版本，除非用户要求发布。
